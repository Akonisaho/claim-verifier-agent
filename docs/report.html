Entry I

The problem

Content teams, financial analysts, investor-relations staff, and journalists reviewing corporate documents — earnings summaries, press releases, internal reports — check each claim against source material by eye. The hardest errors to catch aren't outright lies: they're claims that are technically true but deceptively framed. A number that's real, but whose context — test conditions, time period, the population it applies to — has been quietly changed or dropped, making an accurate number misleading. A tired human reviewer, or a plain AI asked "is this accurate?", sees the number match and waves the claim through.

That is exactly the class of error that causes real reputational and financial harm: a correct-sounding statistic used to imply something the underlying data doesn't support. The domain was chosen deliberately — financial and corporate communications give exact, unambiguous ground truth. A number either matches a filing or it doesn't.

Entry II

Architecture

No retrieval framework, vector database, or agent-orchestration library. Source material is provided directly per case, and both pipelines are plain HTTP calls to a local, free, open-weight model (llama3.2:3b) served via Ollama.

What it does not do

Never determines intent — no "this is fraud" conclusions, only "this doesn't match" or "context was altered." Never fact-checks opinions or forward-looking predictions. Never publishes or acts on its own — every result is a report for a human editor. Never searches the open internet — verifies only against source material the user explicitly provides.

Entry IV

Security & CI gates

Five checks run on every push. None are decorative — each one caught a real issue during development.

01 · Secret scan

gitleaks

Full git-history scan for committed credentials. Expected result is always zero — this project needs no API keys anywhere.

02 · Lint, SAST & dependency audit

ruff · bandit · pip-audit · pytest

pip-audit already caught real CVEs in the originally-pinned requests and pytest versions — both bumped to patched releases before this check ever passed.

03 · Dockerfile lint

hadolint

Standard best-practice checks: non-root user, layer hygiene.

04 · Container scan

Trivy — vulnerability + license

ignore-unfixed is deliberate: the base image carries a few Debian OS CVEs with no upstream fix yet — true of any stock python:3.12-slim pull. The license scan is scoped to this project's own dependencies, since scanning the base OS would flag roughly 300 GPL/LGPL findings on system packages like bash and tar — normal for any Debian image, not something this project controls.

05 · Submission completeness

Required-files check

Confirms README, CHANGELOG, REPRODUCE, Dockerfile, and requirements.txt exist before anything else is evaluated.

Entry V

Reproducibility

Total cost: zero. No API key, no billing account, no signup.

  1. 01git clone the repository
  2. 02./setup.sh — pulls llama3.2:3b, builds the Docker images
  3. 03docker compose run verifier python evaluate.py — runs both pipelines, writes evidence/results.md

Measured, not guessed

Runtime on CPU (no GPU) for all 10 cases: baseline roughly 4-6.5 minutes, verifier roughly 19-23 minutes — two model calls per claim, noticeably longer. These figures replaced earlier pre-launch estimates once real runs contradicted them.

Verified independently three times: two direct runs on the development machine, confirmed byte-identical after fixing a real non-determinism bug (below), plus one full fresh-clone run following this exact path, producing the same 7/10 · 7/10 · 4/10 result.

The hard case

case_09: a compound claim, one true part (revenue +15%) and one false part (headcount claimed down 10%, source says up 4%). Atomic extraction correctly split and verified each part independently — roll-up correctly took the CONTRADICTED verdict rather than averaging into a false "mostly true." The audit flag over-fired here (True vs. ground truth False) — a real, honestly-reported limitation, not smoothed over.

Hot take

For an agent whose whole job is catching misleading framing, reproducibility is a correctness precondition, not a nice-to-have. A verifier that gives a different answer each run isn't more or less accurate on any single question — it means "accuracy" from any one run is close to meaningless until the pipeline is confirmed deterministic.
